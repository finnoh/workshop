👥 Version Control

Understanding Version Control​

Version control is essentially a time machine for your code and documents. It allows you to track changes systematically over time, making it easier to collaborate with others, experiment with new features safely, revert mistakes when they happen, and document why specific changes were made. For researchers, version control provides a reliable way to maintain the integrity and history of your work.

Git in a Nutshell​

Git tracks changes to your files as a series of "commits" - snapshots of your project at specific points in time. Each commit serves as a checkpoint you can return to if needed.

Every commit in Git contains several key pieces of information:

  • A unique identifier (hash) that distinguishes it from all other commits
  • A message explaining what changes were made and why
  • Author information and timestamp showing who made the change and when
  • Links to previous commit(s), creating a chain of project history

This commit structure creates a powerful historical record of your project's evolution, allowing you to understand how your work developed over time and who contributed what changes.

Why Would You Use Git?​

Version control with Git offers distinct benefits both for individual researchers and collaborative teams.

For Individual Researchers​

When working alone, Git helps you track progress over time, creating a detailed history of your research project. This allows you to experiment with new approaches without fear of losing your original work. You can create branches to test different methodologies while keeping your main project intact. Git also enables seamless work across multiple computers, ensuring you always have access to the latest version of your files.

For Research Collaboration​

In collaborative settings, Git truly shines by allowing multiple researchers to work on the same files simultaneously. The system automatically merges compatible changes and flags potential conflicts for resolution. Every modification is tracked with the contributor's information, creating clear accountability and making it easy to understand who changed what and why.

info

GitHub serves as a remote repository for Git projects - think of it as Google Drive for your code and research files. It provides a centralized location where all collaborators can access the project, with additional features like issue tracking and project management tools.

Project Initialization​

Let's walk through a typical research workflow using Git and GitHub, starting with project setup.

When beginning a new research project, you'll first initialize a Git repository in your project folder. This creates the necessary structure for Git to track changes to your files.

# Initialize local repository
git init
git add .
git commit -m "initial project setup"

# Connect to GitHub
git remote add origin https://github.com/researcher/sales-analysis.git
git push -u origin main

This initial setup creates your first commit containing the basic project structure. The directory might include your main document file (like a Quarto document), data folder, and source code directory. Connecting to GitHub allows you to back up your work remotely and share it with collaborators.

Data Preprocessing​

As your research progresses, you'll make changes to your files. For example, you might add code for data preprocessing:

# Create and commit preprocessing code
git add src/preprocess.py
git commit -m "preprocessing the data"

# Local commit only (not pushed yet)
# Changes exist only on this computer

At this stage, you've created a new commit in your local repository that contains your preprocessing code. This commit exists only on your computer until you push it to GitHub. The commit message "preprocessing the data" provides a clear description of what changes were made.

Creating Branches & Push​

Branches are one of Git's most powerful features, allowing parallel development paths within the same project. They're especially useful for collaborative research where different team members work on separate aspects of the project.

# Push latest changes to GitHub
git push origin main

# Create branches for different tasks
git branch modelOLS
git branch lit_review

# Push branches to GitHub so collaborators can see them
git push -u origin modelOLS
git push -u origin lit_review

In this example, we've created two branches: one for developing a statistical model (modelOLS) and another for working on the literature review (lit_review). By pushing these branches to GitHub, they become available to all collaborators.

Model Development (Researcher A)​

With branches established, different researchers can work independently on their assigned tasks. Researcher A might focus on implementing a statistical model:

# Researcher A: Clone repository and switch to assigned branch
git clone https://github.com/researcher/sales-analysis.git
cd sales-analysis
git checkout modelOLS

# Work on OLS model implementation
git add src/ols_model.py
git commit -m "implement OLS regression"
git add src/evaluate.py
git commit -m "add model evaluation metrics"

# Local commits only (not pushed yet)

Researcher A has created two commits on their branch, implementing an OLS regression model and adding evaluation metrics. These changes are isolated to the modelOLS branch, allowing them to work without affecting the main project or other branches.

Literature Review (Researcher B)​

Meanwhile, Researcher B can work on the literature review in their own branch:

# Researcher B: Clone repository and checkout literature branch
git clone https://github.com/researcher/sales-analysis.git
cd sales-analysis
git checkout lit_review

# Add literature review materials
git add literature/
git add paper_sections/background.qmd
git commit -m "add key papers review"
git add paper_sections/theory.qmd
git commit -m "develop theoretical framework"

# Local commits only (not pushed yet)

Researcher B has added content for the literature review, organized in separate files for background research and theoretical framework. Like Researcher A, these changes are isolated to their specific branch.

Push Development Work to GitHub​

Once researchers have made progress on their respective tasks, they can push their changes to GitHub and create pull requests to propose merging their work into the main project:

# Push RF model changes
git push -u origin modelRF

# Create Pull Requests via GitHub
# (Done through web interface or GitHub CLI)
gh pr create --base modelOLS --head modelRF --title "Random Forest Implementation"
gh pr create --base main --head lit_review --title "Literature Review Draft"

Pull requests (PRs) are a GitHub feature that allows team members to review changes before they're merged into the target branch. They provide a platform for discussion, feedback, and quality control.

Merge Literature Review​

After review and approval, the literature review can be merged into the main branch:

# Approve and merge PR on GitHub
# (Through web interface or GitHub CLI)
gh pr merge 1 --merge

# Update local repository
git checkout main
git pull origin main
git add paper.qmd
git commit -m "first draft lit review"
git push origin main

This process integrates the literature review work into the main project. The git pull command ensures your local copy is updated with the changes from GitHub.

Merge Random Forest Model​

Similarly, model implementations can be merged after review:

# Merge RF model PR on GitHub
gh pr merge 2 --merge

# Update local modelOLS branch
git checkout modelOLS
git pull origin modelOLS

# Create benchmark comparing models
git add src/model_benchmark.py
git commit -m "created benchmark of models"
git push origin modelOLS

In this case, a Random Forest model implementation is merged into the OLS model branch, followed by the creation of a benchmark to compare the different models.

Final Results & GitHub Pages​

Finally, all components can be merged into the main branch to complete the project:

# Create pull request for final merge
gh pr create --base main --head modelOLS --title "Model Results"

# After PR approval, update locally
git checkout main
git pull origin main
git merge modelOLS
git add results/
git commit -m "first results"

# Push final changes and create release
git push origin main
gh release create v1.0.0 --title "Initial Research Results"

# Setup GitHub Pages with Quarto
quarto render docs --to html 
git add docs
git commit -m "add documentation website"
git push origin main

This final stage includes creating a release (a tagged snapshot of your project) and setting up GitHub Pages to publish your results as a website. The release can be assigned a DOI for citation purposes, making your research more accessible and citable.

tip

Creating a GitHub release with a DOI through services like Zenodo makes your research output citable and helps fulfill open science requirements. The GitHub Pages website provides an accessible way to share your findings with the broader research community.

Through this workflow, Git and GitHub provide a structured approach to research collaboration, ensuring that all contributions are tracked, reviewed, and properly integrated into the final project.
